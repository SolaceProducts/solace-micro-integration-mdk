# Prepare Configuration

Read a technology overview report (generated by `analyze-integration-tech`) and the `configuration_template.md` template, then produce a pre-filled `configuration.md` at the workspace root. Fields that can be confidently determined from the overview are auto-filled; everything else is marked with `🔴 TODO` for the user to complete manually.

## Quick Start

```bash
/prepare-config overview-amazon-sqs.md
/prepare-config overview-mysql.md
/prepare-config overview-apache-kafka.md
```

**Input**: Relative path (from workspace root) to a technology overview report.
**Output**: `configuration.md` at workspace root with auto-filled and TODO-marked fields.

## Scope

**What this skill does:**
- Reads the technology overview report specified as the argument
- Reads `configuration_template.md` from the workspace root
- Extracts technology name, SDK dependency, Testcontainers info, and binder info from the overview
- Produces `configuration.md` with auto-filled values and `🔴 TODO` markers
- Prints an execution summary table showing which fields were filled vs marked TODO

**What this skill does NOT do:**
- Does not run any build commands or Maven operations
- Does not validate Maven dependencies against Maven Central
- Does not create or modify any project directories or source files
- Does not invoke other skills
- Does not read or modify any file other than writing `configuration.md`

## Step Execution Rules

Each step must complete successfully before the next step begins. Do not skip ahead, parallelize steps, or begin a step while a previous step is incomplete.

## Implementation Instructions

### Step 1: Validate parameter

The skill receives a single argument — the relative path to the technology overview file (e.g., `overview-amazon-sqs.md`).

**Validation:**
1. If no argument is provided, print: **"Missing argument — provide the path to a technology overview file (e.g., `/prepare-config overview-amazon-sqs.md`)"** and stop.
2. Use Read to verify the file exists at the workspace root. If the file does not exist, print: **"Overview file not found: `{argument}`"** and stop.

### Step 2: Discover configuration template

Use Glob to locate `configuration_template.md` at the workspace root.

**On failure — hard stop:**
- Print: **"Template not found — `configuration_template.md` must exist at the workspace root."**
- Stop. Do not create any files.

### Step 3: Check for existing configuration.md

Use Glob to locate `configuration.md` at the workspace root.

**If `configuration.md` exists — hard stop:**
- Print: **"⚠️ `configuration.md` already exists at the workspace root. This skill will not overwrite an existing configuration. Please rename or move the existing file (e.g., `configuration_backup.md` or `configuration_old.md`) and rerun `/prepare-config`."**
- Stop. Do not create or modify any files.

### Step 4: Read both files

Read the full contents of:
1. `configuration_template.md` — to understand the template structure, all sections, variables, and the table format
2. The overview report file — to extract technology-specific data

### Step 5: Extract data from the overview report

Parse the overview report to extract the following information. Each extraction target references the specific section of the overview where the data is found.

#### 5a. Technology name (from report title)

The first line of the overview report is a heading like `# Amazon SQS Integration Technology Analysis`. Extract the technology name — the first word(s) before "Integration Technology Analysis".

Derive three name forms:
- `TECH_NAME_LOWER` — lowercased, spaces replaced with hyphens (e.g., `amazon-sqs`, `apache-kafka`, `mysql`)
- `TECH_NAME_UPPER` — uppercased, spaces replaced with hyphens (e.g., `AMAZON-SQS`, `APACHE-KAFKA`, `MYSQL`)
- `TECH_NAME_CLASS_NAME_USE` — the exact capitalisation from the report title (e.g., `AmazonSQS`, `MySQL`, `ApacheKafka`)

#### 5b. Client SDK dependency (Section 3.1)

Locate the **first** Maven `<dependency>` XML block in Section 3.1 ("Java Client APIs"). Extract the complete `<dependency>...</dependency>` element and collapse it to a single line for `CLIENT_SDK_DEPENDENCY`.

If Section 3.1 contains no Maven dependency block, mark `CLIENT_SDK_DEPENDENCY` as `🔴 TODO — no SDK dependency found in overview Section 3.1`.

#### 5c. Test support strategy and Testcontainers dependency (Section 5.1)

Locate Section 5.1 ("Testcontainers Integration" or "TestContainer Integration"):

- If Section 5.1 states that official Testcontainers support **is available** and contains a Maven `<dependency>` block:
  - Set `TEST_SUPPORT_STRATEGY` = `A`
  - Extract the complete `<dependency>...</dependency>` element, collapse to a single line, and set as `TESTCONTAINERS_MODULE_DEPENDENCY`
- If Section 5.1 states **no official Testcontainers** support but Section 5.2 documents official Docker images:
  - Set `TEST_SUPPORT_STRATEGY` = `B`
  - Leave `TESTCONTAINERS_MODULE_DEPENDENCY` empty (its section in the template will remain commented out or be omitted)
- Otherwise:
  - Set `TEST_SUPPORT_STRATEGY` = `🔴 TODO — could not determine test strategy from overview`

#### 5d. Spring Cloud Stream binder info (Section 3.5)

Locate Section 3.5 ("Spring Cloud Stream Binder"):

- If Section 3.5 contains the phrase "existing Spring Cloud Stream binder is available" and the binder project is **actively maintained** (not archived):
  - Set `BINDER_SKIP_GENERATION` = `true`
  - Extract the GitHub repository URL → set as `BINDER_3PARTY_SOURCE_URL`
  - Extract the **runtime dependency** `<dependency>` block (not the BOM, not the `<dependencyManagement>` block — the actual runtime `<dependency>`). If the runtime dependency has no `<version>` element (version managed by BOM), look for the latest release version mentioned in the "Project Status" line of Section 3.5 and add it as a `<version>` element. Collapse to a single line → set as `BINDER_3PARTY_DEPENDENCY`
- If Section 3.5 states no binder exists, or the binder is archived/unmaintained:
  - Set `BINDER_SKIP_GENERATION` = `false`
  - Leave `BINDER_3PARTY_SOURCE_URL` empty
  - Leave `BINDER_3PARTY_DEPENDENCY` empty

### Step 6: Fill the template

Start from the structure and content of `configuration_template.md`. For each variable row in each table, fill the **Configuration Value** column according to the rules below. The result must be valid markdown with the same sections, tables, headings, and notes as the template.

#### Auto-filled from overview report

| Variable | Value |
|---|---|
| `TECH_NAME_LOWER` | Extracted in Step 5a |
| `TECH_NAME_UPPER` | Extracted in Step 5a |
| `TECH_NAME_CLASS_NAME_USE` | Extracted in Step 5a |
| `TECH_OVERVIEW_PATH` | The argument value passed to this skill (the overview file path) |
| `CLIENT_SDK_DEPENDENCY` | Extracted in Step 5b |
| `TEST_SUPPORT_STRATEGY` | Determined in Step 5c |
| `TESTCONTAINERS_MODULE_DEPENDENCY` | Extracted in Step 5c (only when strategy = A) |
| `BINDER_SKIP_GENERATION` | Determined in Step 5d |
| `BINDER_3PARTY_SOURCE_URL` | Extracted in Step 5d (only when 3rd-party binder exists) |
| `BINDER_3PARTY_DEPENDENCY` | Extracted in Step 5d (only when 3rd-party binder exists) |

#### Auto-filled using naming conventions (derived from `TECH_NAME_LOWER`)

| Variable | Convention |
|---|---|
| `TEST_SUPPORT_ARTIFACT_ID` | `test-support-{TECH_NAME_LOWER}` |
| `BINDER_ARTIFACT_ID` | `spring-cloud-stream-binder-{TECH_NAME_LOWER}` |
| `INTEGRATION_APP_ARTIFACT_ID` | `solace-micro-integration-{TECH_NAME_LOWER}` |
| `ROOT_ARTIFACT_ID` | `solace-micro-integration-{TECH_NAME_LOWER}-parent` |
| `MI_CONTAINER_IMAGE_NAME` | `solace-micro-integration-{TECH_NAME_LOWER}` |

#### Always marked `🔴 TODO`

These variables always receive a TODO marker regardless of what the overview contains. Write the marker in the **Configuration Value** column.

| Variable | TODO Value |
|---|---|
| `TARGET_PROJECT_FOLDER` | `🔴 TODO` |
| `PROJECT_ROOT_GROUP_ID` | `🔴 TODO` |
| `PROJECT_VERSION` | `🔴 TODO` |
| `BINDER_BUILD_PARENT_VERSION` | `🔴 TODO` |
| `BINDER_TYPE` | `🔴 TODO` |
| `BINDER_PACKAGE` | `🔴 TODO` |
| `MI_PACKAGE` | `🔴 TODO` |

#### Section 6 — always TODO

**Every** variable in Section 6 ("Platform & Framework Versions") must be marked `🔴 TODO` regardless of any information in the overview. This includes:
- `MICRO_INTEGRATION_PLATFORM_BOM_VERSION` → `🔴 TODO`
- `MICRO_INTEGRATION_BUILD_PARENT_VERSION` → `🔴 TODO`
- `JDK_PATH` → `🔴 TODO`
- `JAVA_VERSION` → `🔴 TODO`
- `HOST_OS` → `🔴 TODO`

#### Fallback rule

Any variable not covered by the tables above that the skill cannot confidently determine from the overview report must also be marked `🔴 TODO — {brief reason}`.

#### Commented-out sections

Preserve the same commented-out section structure as the template. If `TEST_SUPPORT_STRATEGY` is `A`, keep Strategy A uncommented and strategies B/C/D commented out (as in the template). If `TEST_SUPPORT_STRATEGY` is `B`, uncomment Strategy B and comment out Strategy A. Follow the same logic for other conditional sections.

### Step 7: Write `configuration.md`

Write the filled template to `configuration.md` at the workspace root.

### Step 8: Print execution summary

Print a summary with two tables:

**Auto-filled fields:**

| Variable | Value | Source |
|---|---|---|
| (list each auto-filled variable) | (the value written) | (e.g., "Overview Section 3.1", "Naming convention", "Skill argument") |

**Fields requiring user input (`🔴 TODO`):**

| Variable | Section | Reason |
|---|---|---|
| (list each TODO variable) | (section number) | (e.g., "User-specific path", "Organisational choice", "Platform version — always requires user input") |

If any data extraction in Step 5 was ambiguous or partially successful, add a **Warnings** section below the tables listing each issue (e.g., "Section 3.5 mentions a binder but project status could not be confirmed — defaulted to `BINDER_SKIP_GENERATION=false`").

### Step 9: Ask user to review

Print: **"Please review `configuration.md` and fill in all fields marked `🔴 TODO` before running downstream skills (`/init-mi-project`, `/add-binder`, etc.)."**
