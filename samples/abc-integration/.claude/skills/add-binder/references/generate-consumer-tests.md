### Test pattern

Each consumer test follows the same three-phase flow. The **universal** parts (TestApplication message reception, ack callbacks, error channel) are the same for every technology. The **SDK-specific** parts differ per technology — use CLAUDE.md, then `configuration.md`, then the overview report at `{TECH_OVERVIEW_PATH}` for the SDK details.

1. **Inject (SDK-specific)** — use the SDK client directly to publish/write a message to the source destination. The consumer binding polls the backend and receives the message.
2. **Verify (universal)** — use `TestApplication.receiveMessage()` to confirm the consumer binding received and processed the message. Assert on payload and headers.
3. **Ack/error verification (mixed)** — verify ack/reject behaviour using SDK-specific methods (e.g., check DLQ for rejected messages) and universal error channel assertions.

### Scope

This test class has exactly **5 test methods** — matching the ABC template. The first 4 test consumer messaging behaviour, the 5th verifies binder health. Do not add additional test methods.

### Transformation rules (in addition to general rules)

- Package declaration → `{BINDER_PACKAGE}`
- Import `TestApplication` with `{BINDER_PACKAGE}.app.TestApplication`
- **Active profile override**: The generated class must override `getActiveProfiles()` to return `new String[]{"consumer"}`. This activates `application-consumer.yml`, which contains only the consumer function definition, consumer binding, and consumer extended properties.

**SDK type replacements** — read from CLAUDE.md **SDK Client** data types section, fall back to overview report at `{TECH_OVERVIEW_PATH}`:
- `AbcClient.AbcOutboundMessage` → the SDK's outbound/write message type (used in inject phase to publish test messages to the backend)
- `AbcClient.AbcInboundMessage` → the SDK's inbound/read message type (if referenced for DLQ/rejected message verification)

**Test-support type replacements** — read from CLAUDE.md **Testing Notes**, fall back to test-support module source:
- `AbcTestContainerWithConnectedClient` → wrapper or proxy class (parameter type injected by JUnit extension into test methods). Depends on test-support architecture: `container-with-client` → e.g., `{Tech}TestContainerWithConnectedClient`; `proxy-service-with-client` → e.g., `{Tech}ProxyServiceWithClient`

### Test methods

1. **`testConsumerBindingSuccessfulProcess`** — happy path: message injected via SDK, received by consumer binding
   - **Inject** (SDK-specific): use `containerWrapper.getClient().publishMessage(SOURCE_DESTINATION, ...)` — replace with the target SDK's write/publish method from CLAUDE.md **SDK Client** publish methods. Construct the SDK's outbound message type with a test payload and a `test-header` header.
   - **Verify** (universal): `application.receiveMessage(10, TimeUnit.SECONDS)` — assert payload equals test payload, assert headers contain `test-header`
   - **No redelivery assertion** (universal): `application.receiveMessage(1, TimeUnit.SECONDS)` — assert null (message was acked, not redelivered)

2. **`testConsumerBindingFailedProcess`** — rejection path: message with `reject_me` header triggers REJECT
   - **Inject** (SDK-specific): publish a message with `reject_me: "true"` header using the SDK client
   - **Verify** (SDK-specific): use Awaitility to wait for the rejected message to appear in the DLQ. Replace `containerWrapper.getClient().getRejectedMessages()` with the target SDK's equivalent from CLAUDE.md **SDK Client** section. If the SDK has no DLQ/rejected message retrieval method, verify rejection by confirming the message is no longer available for polling from the source destination.

3. **`testDefaultBindingConfiguration`** — verifies extended binding property defaults
   - **Verify** (universal): use `CapturedOutput` (from `@ExtendWith(OutputCaptureExtension.class)`) and Awaitility to assert that the expected polling interval appears in the log output. The ABC template checks for `"Polling interval: 1000 ms"` — adapt the log message pattern to match the target binder's inbound channel adapter logging.
   - This test validates that extended consumer properties from `application-consumer.yml` are correctly applied.

4. **`testConsumerBindingPublishesToErrorChannelOnErrors`** — error channel: message with `cause_error` header triggers error
   - **Inject** (SDK-specific): publish a message with `cause_error: "true"` header using the SDK client
   - **Error channel verification** (universal): `application.readMessageReceivedOnErrorChannel(10, TimeUnit.SECONDS)` — assert `ErrorMessage` is not null, assert `originalMessage.getPayload()` equals the test payload
   - **Requeue/reject verification** (SDK-specific): use Awaitility to verify the message was requeued/rejected by the ack callback. Replace with the target SDK's DLQ/rejected message retrieval — same adaptation as test 2.

5. **`testHealth`** — verifies binder health endpoint reports UP status
   - Uses `getMockMvc().perform(get("/actuator/health"))` from the base class
   - Asserts:
     - `status().isOk()`
     - `jsonPath("components.binders.components.{BINDER_NAME}").exists()`
     - `jsonPath("components.binders.components.{BINDER_NAME}.status").value("UP")`
   - Everything else (MockMvc injection, GET path, status check, value `"UP"`) — universal, copy as-is from the ABC template
