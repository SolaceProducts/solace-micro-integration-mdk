# Generate Producer

This file generates the producer-specific binder implementation: the outbound message handler and its integration test. All shared infrastructure (properties, IOUtil, provisioner, binder class, configuration, META-INF) is already generated by `generate-shared.md`, and shared test infrastructure (profile-specific application YAML files, TestApplication, AbstractBase) is already generated by `generate-common-tests.md`, before this file is invoked. The sync producer test class is generated by `generate-sync-producer-tests.md` (delegated from Step 3), and the async producer test class by `generate-async-producer-tests.md` (delegated from Step 4, conditional on `PRODUCER_IS_ASYNC`).

## Step 1: Generate outbound message handler

**Blocked by:** Nothing — this is the first step. All prerequisites (properties, IOUtil, provisioner, binder class) are already generated by `generate-shared.md`.

Read the ABC template `AbcOutboundMessageHandler.java` for the structural pattern.

| Blueprint | Output |
|---|---|
| `{ABC_MAIN}/outbound/AbcOutboundMessageHandler.java` | `{BINDER_TARGET_SRC_DIR}/outbound/{Tech}OutboundMessageHandler.java` |

**Transformation rules (in addition to general rules):**

- Replace package, class names, and imports
- Replace `AbcClient` with the actual SDK client class from CLAUDE.md SDK Client section
- Replace `IOUtil.createAbcClient(...)` with `IOUtil.create{Tech}Client(...)`
- **`start()`** — create client via IOUtil. Call client start/connect if the SDK requires an explicit connect step.
- **`handleMessage(Message<?>)`** — follow the ABC template `handleMessage` / `publishSync` / `publishAsync` pattern. The structure depends on `PRODUCER_IS_ASYNC` (determined in `plan-binder-impl.md`):

  **Common steps (both modes):**
  1. Guard: throw `MessagingException` if not running
  2. Resolve destination (check `BinderHeaders.TARGET_DESTINATION` for dynamic routing, fall back to bound destination). Trim the resolved destination.
  3. Do NOT build the SDK outbound message here — message construction is deferred to the single/batch publish methods because batch messages carry `List<Object>` payloads with per-message headers that must be unpacked individually.

  **When `PRODUCER_IS_ASYNC=true`:**
  4. Branch: if `producerProperties.getExtension().isAsync()` call `publishAsync`, else call `publishSync`
  5. Generate private `publishAsync(destination, message)` — extract `PublishAcknowledgmentCallback` from message headers, then **batch router**: if `message.getHeaders().containsKey(BinderHeaders.BATCH_HEADERS)` delegate to `publishBatchAsync`, else delegate to `publishSingleAsync`. Pass the extracted callback as a parameter to both delegates.
  6. Generate private `publishSync(destination, message)` — **batch router**: if `message.getHeaders().containsKey(BinderHeaders.BATCH_HEADERS)` delegate to `publishBatchSync`, else delegate to `publishSingleSync`
  7. Generate private `publishSingleAsync` — build SDK outbound message from payload and **filtered** headers (call `filterHeaders(message.getHeaders())`), adapt SDK async publish method, enforce non-null `publishAckCallback` via `Objects.requireNonNull`, wire `publishAckCallback.onPublishSuccess()` / `onPublishFailure(e)`, send to error channel on failure
  8. Generate private `publishSingleSync` — build SDK outbound message from payload and **filtered** headers (call `filterHeaders(message.getHeaders())`), adapt SDK sync publish method, throw `MessagingException` on failure, send to error channel on failure
  9. Generate private `publishBatchAsync` — see **Batch publish methods** below
  10. Generate private `publishBatchSync` — see **Batch publish methods** below

  **When `PRODUCER_IS_ASYNC=false`:**
  4. Call `publishSync` directly (no callback extraction, no branching)
  5. Generate private `publishSync(destination, message)` — **batch router**: if `message.getHeaders().containsKey(BinderHeaders.BATCH_HEADERS)` delegate to `publishBatchSync`, else delegate to `publishSingleSync`
  6. Generate private `publishSingleSync` — build SDK outbound message from payload and **filtered** headers (call `filterHeaders(message.getHeaders())`), adapt SDK sync publish method, throw `MessagingException` on failure, send to error channel on failure
  7. Generate private `publishBatchSync` — see **Batch publish methods** below
  8. Do NOT generate `publishAsync`, `publishSingleAsync`, `publishBatchAsync`, do NOT add `isAsync` branching, do NOT extract `PublishAcknowledgmentCallback`

  ### Header filtering (mandatory)

  The outbound message handler **must** include a `filterHeaders` static helper method. Spring Integration injects internal headers (`id`, `timestamp`) and the binder framework adds `ConnectorBinderHeaders.PUBLISH_ACKNOWLEDGMENT_CALLBACK` — these must be stripped before sending to the target system. **All** publish methods (single and batch, sync and async) must call `filterHeaders()` when building SDK outbound messages.

  ```java
  public static Map<String, Object> filterHeaders(MessageHeaders headers) {
      Map<String, Object> filteredHeaders = new HashMap<>(headers);
      filteredHeaders.remove(ConnectorBinderHeaders.PUBLISH_ACKNOWLEDGMENT_CALLBACK);
      filteredHeaders.remove(MessageHeaders.ID);
      filteredHeaders.remove(MessageHeaders.TIMESTAMP);
      return filteredHeaders;
  }
  ```

  **Required imports:** `java.util.HashMap`, `java.util.Map`, `org.springframework.messaging.MessageHeaders`, `com.solace.connector.core.io.header.ConnectorBinderHeaders`

  ### Batch publish methods

  Batch publishing is always generated. The dispatch strategy depends on `SDK_HAS_BATCH_PUBLISH` from CLAUDE.md:

  **Common batch extraction logic (shared by both async and sync batch methods):**
  1. Extract `List<MessageHeaders> batchedHeaders` from `message.getHeaders().get(BinderHeaders.BATCH_HEADERS)`
  2. Validate: throw `IllegalArgumentException` if `batchedHeaders` is null
  3. Extract `List<Object> batchedPayloads` by casting `message.getPayload()`
  4. Validate: throw `IllegalArgumentException` if `batchedHeaders.size() != batchedPayloads.size()`
  5. Build `List<{Tech}OutboundMessage>` using `IntStream.range(0, batchedPayloads.size())` to pair each payload with its corresponding **filtered** per-message headers via `filterHeaders(batchedHeaders.get(i))`

  **`publishBatchAsync` callback handling** (applies to both `SDK_HAS_BATCH_PUBLISH` modes): `publishBatchAsync` must accept `publishAckCallback` as a parameter (passed from `publishAsync`) and enforce non-null via `Objects.requireNonNull(publishAckCallback, ...)` before any batch processing.

  **When `SDK_HAS_BATCH_PUBLISH=true` (preferred — native batch API):**
  - `publishBatchSync`: call the SDK's batch sync publish method (e.g., `client.publishMessages(destination, batch)`) passing the `List` of SDK outbound messages. Wrap in try/catch, send to error channel on failure, throw `MessagingException`.
  - `publishBatchAsync` (only when `PRODUCER_IS_ASYNC=true`): call the SDK's batch async publish method. The wiring depends on the SDK's async pattern:
    - **Future-returning** (e.g., `CompletableFuture<List<String>> publishMessagesAsync(destination, batch)`): apply `orTimeout`, chain `.thenAccept()` to call `publishAckCallback.onPublishSuccess()`, chain `.exceptionally()` to call `publishAckCallback.onPublishFailure(cause)` and send to error channel.
    - **Callback-accepting** (e.g., `void publishMessagesAsync(destination, batch, onSuccess, onError)`): pass `publishAckCallback.onPublishSuccess()` as the success callback and a lambda that calls `publishAckCallback.onPublishFailure(cause)` and sends to error channel as the error callback. Enforce timeout externally via a `ScheduledExecutorService` or wrapping in a `CompletableFuture` with `orTimeout`.

  **When `SDK_HAS_BATCH_PUBLISH=false` (fallback — sequential single-message dispatch):**
  - `publishBatchSync`: iterate the built list and call the SDK's single sync publish method for each message sequentially. On first exception, stop immediately — do not send remaining messages. Send the exception to error channel and throw `MessagingException`. Messages already sent before the failure are not rolled back (at-least-once semantics).
  - `publishBatchAsync` (only when `PRODUCER_IS_ASYNC=true`): submit a single task to a single-thread executor that iterates the built list and calls the SDK's single **sync** publish method for each message sequentially. Wrap the executor submission in a `CompletableFuture`: on successful completion of all sends, call `publishAckCallback.onPublishSuccess()`; on any exception, call `publishAckCallback.onPublishFailure(cause)` and send to error channel. Apply `orTimeout` to the future. Messages already sent before a failure are not rolled back (at-least-once semantics).

    **Executor lifecycle** — when `SDK_HAS_BATCH_PUBLISH=false` and `PRODUCER_IS_ASYNC=true`, the outbound message handler must declare an `ExecutorService` field (e.g., `private ExecutorService batchExecutor`). Create it in `start()` via `Executors.newSingleThreadExecutor()` and shut it down in `stop()` via `batchExecutor.shutdownNow()`. This field is not needed when `SDK_HAS_BATCH_PUBLISH=true` (native batch API handles threading internally).

    Reference pattern:
    ```java
    CompletableFuture.runAsync(() -> {
        for ({Tech}OutboundMessage msg : batch) {
            client.publishMessage(destination, msg);
        }
    }, batchExecutor)
    .orTimeout(timeoutMs, TimeUnit.MILLISECONDS)
    .thenRun(() -> publishAckCallback.onPublishSuccess())
    .exceptionally(e -> {
        Throwable cause = e instanceof CompletionException ? e.getCause() : e;
        if (errorChannel != null) {
            errorChannel.send(new ErrorMessage(cause, message));
        }
        publishAckCallback.onPublishFailure(cause);
        return null;
    });
    ```
- **`stop()`** — close/disconnect client using the SDK's close method from CLAUDE.md
